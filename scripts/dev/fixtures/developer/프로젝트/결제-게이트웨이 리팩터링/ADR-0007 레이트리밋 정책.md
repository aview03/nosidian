# ADR-0007 레이트리밋 정책

상태: **Proposed** · 결정자: 동민, 지수 · 관련: [[장애 회고 2026-11-05]], [[프로젝트 개요]]

## 배경
11/05 장애에서 재시도 폭주(retry storm)로 승인 API가 포화됐다. 클라이언트가 429를 받아도 즉시 재시도해 부하가 더 커졌다. 게이트웨이에서 **일관된 레이트리밋**과 `Retry-After` 응답이 필요하다.

## 선택지
| 방식 | 장점 | 단점 |
| --- | --- | --- |
| IP 단위 | 구현 단순, 인증 전에도 적용 | NAT 뒤 사용자 다수가 한 번에 막힘 |
| 사용자(토큰) 단위 | 공정함, 오남용 추적 쉬움 | 인증 이후에만 가능, Redis 키 증가 |
| 혼합 (IP 느슨 + 사용자 엄격) | 둘의 장점 | 설정 복잡 |

> [!tip] 제안
> **혼합**: IP는 분당 600회로 느슨하게, 사용자는 분당 60회로 엄격하게. 초과 시 `429` + `Retry-After`.

## 구현 스케치
```ts
// gateway/src/middleware/rateLimit.ts
import { Redis } from 'ioredis'

const WINDOW_SEC = 60
const LIMITS = { ip: 600, user: 60 } as const

export async function rateLimit(redis: Redis, key: string, limit: number) {
  const bucket = `rl:${key}:${Math.floor(Date.now() / 1000 / WINDOW_SEC)}`
  const count = await redis.incr(bucket)
  if (count === 1) await redis.expire(bucket, WINDOW_SEC)
  const retryAfter = WINDOW_SEC - (Math.floor(Date.now() / 1000) % WINDOW_SEC)
  return { allowed: count <= limit, remaining: Math.max(0, limit - count), retryAfter }
}
```

```nginx
# 임시 완화(게이트웨이 전환 전): ingress-nginx
limit_req_zone $binary_remote_addr zone=pay:10m rate=10r/s;
location /v1/payments {
    limit_req zone=pay burst=20 nodelay;
    limit_req_status 429;
}
```

## 결과
- 429 응답에 `Retry-After`를 포함하면 모바일 SDK가 지수 백오프로 재시도한다.
- 미결: 사용자 단위 기준을 **계정**으로 할지 **기기**로 할지 → 할 일에 안건으로 올림.
