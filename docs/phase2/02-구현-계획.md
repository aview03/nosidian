# Phase 2 구현 계획: 노트·일정 앱 → 범용 프로젝트 운영 앱

> **상태**: 결정 반영, P2-1 구현 중(업무 인덱스·내 업무·편집기·프로젝트 허브 완료 / 칸반·템플릿 남음). 확정된 사항은 맨 아래 "결정 사항" 참고. 구현 현황은 [../WORK.md](../WORK.md).
> **입력**: [01 Codex 제안](01-codex-제안-범용-프로젝트-관리.md) + 사내 백오피스 설계 문서(로컬 참고용) + 현재 코드(README, `src/lib/*`).
> **원칙**: 사내 업무(입찰·계약·정산 등)를 제품에 박지 않는다. 범용 "업무 객체 + 뷰"를 먼저 만들고 업무별 기능은 나중에 "프로젝트 팩"으로 얹는다.

---

## 1. 한 문장 정의

> 문서·할 일·일정·결정·파일이 **하나의 프로젝트 안에서 연결**되고, 그것이 전부 **사람이 읽을 수 있는 마크다운**으로 저장되는, 서버 없는 프로젝트 운영 앱.

차별점 두 가지를 지킨다. ① 데이터는 열려 있다(`.md`). ② "내 업무"는 저장하지 않고 **원본 노트에서 매번 파생**한다.

## 2. 이미 맞아떨어지는 것 (새로 만들 필요가 없는 기반)

Codex 제안과 백오피스 설계가 공통으로 말하는 원칙이 **Nosidian 의 설계 원칙과 이미 같다.** 이것이 이 방향이 현실적인 이유다.

| 제안/설계의 원칙 | Nosidian 에서 이미 있는 것 |
|---|---|
| **파생은 저장하지 않는다**(알림·대기열 표를 따로 두면 원본과 어긋난다) | 링크 인덱스·태그·그래프·캘린더가 모두 노트에서 파생(`buildIndex`, `buildCalendar`), 내용 해시 캐시 |
| 마크다운이 원장 | 일정도 노트의 체크리스트 한 줄 |
| 노트에 타입을 부여 | 프론트매터 파싱(`ParsedNote.fm`, `splitFrontmatter`)과 속성 패널이 이미 있음. 일정은 프론트매터 `date` 노트를 이미 인식 |
| 같은 데이터의 여러 뷰 | 캘린더 월/주/목록·위젯이 이미 "같은 일정의 여러 뷰" |
| 눌러서 처리 위치로 이동 | `openPath`/딥링크/위젯 → 앱 이동 |
| 모든 사람이 비개발자 | 일정 편집기(GUI)·자연어 입력 패턴이 이미 검증됨 |

## 3. 제안 ↔ 현재 구조 대조 (무엇이 비어 있나)

| 제안 | 현재 | 비어 있는 것 | 단계 |
|---|---|---|---|
| 노트를 업무 객체로(`type: project/task/…`) | `fm` 은 읽지만 타입 개념·스키마·편집 UI 없음. 일정 파서는 **Daily 노트나 `@날짜` 줄만** 인식 | 타입 레지스트리, 속성 편집 UI, **모든 노트의 체크리스트를 업무로 인덱싱** | P2-1 |
| 할 일에 담당·마감·우선순위·상태 | 체크리스트는 완료/미완료 + 일정 토큰(`@`, `end:`, `repeat:`, `until:`) | `due:` `owner:` `p:` 토큰과 `[~]` `[>]` 등 상태, 편집 GUI | P2-1 |
| 프로젝트 허브 | 폴더 트리·백링크만 | 프로젝트 개념(루트·소속 판정), 허브 화면(개요·할 일·일정·문서·결정) | P2-1 |
| **내 업무** 통합 화면 | "오늘" 탭(오늘 일정 + 지난 미완료 14일 + 향후 7일) | 기한 초과·담당자 없음·답변 대기·미결을 가로지르는 통합 대기열 | P2-1 |
| 표·칸반 뷰 | 없음 | 타입 노트를 표/칸반으로, 칸반 이동 시 `status:` 편집 | P2-1 |
| 프로젝트 템플릿 | 예제 vault 생성 코드(`demo*.ts`)뿐 | 템플릿 정의·폴더+문서 생성·마감일 역산 | P2-1 |
| 결정·미결 관리 | 없음 | 협의 항목(질문/답/미결/닫힘), **닫을 때 결론 강제**, 다시 물을 날 | P2-2 |
| 받은 편지함 | 없음(빠른 입력은 일정 전용) | 분류 전 임시 수집함 | P2-2 |
| 타임라인(변경 이력) | 노트 단위 mtime 뿐 | 의미 있는 사건만 골라 보여 주는 활동 피드 | P2-2 |
| 건강도·조기경보 | 없음 | 파생 지표 + **문턱을 한 곳에** | P2-2 |
| 저장된 필터/사용자 정의 뷰 | 없음 | 필터 모델 + GUI 빌더 | P2-2 |
| 고객·계약·비용, 리소스 | 없음 | 프로젝트 팩 | P2-3 (보류) |
| 조직 협업(권한·승인·감사) | 서버 없음, 파일 단위 동기화 | 선택형 서버 | P2-4 (보류) |

## 4. 핵심 설계

### 4.1 데이터는 노트 안에 둔다 — 스키마

**타입 노트(프론트매터)** — 기존 `date:`/`end:` 일정 노트와 같은 방식.

```yaml
---
type: project            # project | meeting | decision | issue | client | resource | report …
status: active           # 타입마다 허용값이 다름 (아래 레지스트리)
owner: 홍길동
start: 2026-11-01
due: 2027-02-28
health: warning          # 사람이 판단한 상태 (시스템 건강도와 별개, 4.5)
---
```

**업무 한 줄(체크리스트)** — 기존 토큰 문법(`key:value`)을 그대로 늘린다.

```
- [ ] 견적서 수정 due:2026-11-12 owner:홍길동 p:1
- [~] 보도자료 초안            # 진행 중
- [>] 상장 재고 확인 side:상대 due:2026-11-12   # 상대 차례(답 대기)
- [x] 영상 이벤트 정책 => 중복 수상 불가로 결정    # 닫을 때 '=> 결론'
```

- 상태 문자: `[ ]` 할 일 · `[~]` 진행 중 · `[>]` 대기(상대 차례) · `[x]` 완료 · `[-]` 접음. Obsidian Tasks 와 호환되는 문자라 다른 도구에서도 읽힌다.
- 토큰: `due:` `owner:` `p:`(1~3) `side:`(me/other) `proj:`([[프로젝트]]) `impact:` 와 결론 `=>`. 기존 `@날짜`(일정), `end:` `repeat:` `until:`(일정)과 공존한다.
- **원칙**: 사람이 직접 써도 되고, GUI 가 같은 줄을 만든다(일정 편집기와 동일한 방식).

### 4.2 소속(프로젝트) 판정 — 규칙 세 가지만

노트는 다음 중 하나면 그 프로젝트에 속한다(우선순위 순).
1. 프론트매터 `project: [[프로젝트명]]` 또는 줄의 `proj:`
2. 프로젝트 노트(`type: project`)가 있는 **폴더 아래**에 있다
3. 프로젝트 노트에서 링크된 노트

여러 규칙이 충돌하면 1이 이긴다. 소속이 없으면 "프로젝트 없음"으로 내 업무에는 나타난다(받은 편지함 성격).

### 4.3 업무 인덱스 — 새 파생 모듈 `src/lib/work.ts`

`buildCalendar` 와 **같은 구조**(파일 내용 해시 캐시 → 파일별 파싱 결과 → 합산)로 만든다. 저장하는 새 데이터는 없다.

```ts
WorkIndex {
  projects: Project[]            // type: project 노트 + 소속 노트 집합 + 파생 건강도
  tasks: Task[]                  // 모든 노트의 체크리스트 한 줄 (상태·due·owner·p·side·proj·결론)
  items: Item[]                  // 협의/결정/이슈 항목 (P2-2)
  byProject: Map<project, …>
}
```
- **내 업무 대기열**은 `tasks`/`items` 위의 **필터 함수**일 뿐이다(기한 초과, 담당자 없음, 답 대기 초과, 미결…). 별도 알림 표를 두지 않는다.
- 각 항목에 **"왜 여기 있나"**(`reason`)를 함께 계산해 화면에 보여 준다.
- 캘린더(`calendar.ts`)와는 `due:` 를 이벤트로도 보여 주는 정도로만 연결한다(한 줄이 업무이자 일정이 되는 경우).

### 4.4 화면 구조

PC 레일(현재 캘린더 / 메모 / 검색)을 다음처럼 확장한다. 관리성 메뉴는 기본 숨김(개인 사용자가 무거운 ERP 로 느끼지 않게).

```
내 업무(홈)  ← 시작 화면 후보
프로젝트     ← 목록 + 허브
캘린더
메모         (현재의 파일 트리)
검색
(관리: 템플릿, 설정 — 필요할 때만)
```
- **프로젝트 허브**: 개요 · 할 일(표/칸반) · 일정 · 문서 · 결정(P2-2) · 파일/링크. 템플릿이 정한 탭만 보인다.
- **뷰 전환**: 같은 타입 노트를 목록/표/칸반으로. 칸반에서 카드를 옮기면 해당 노트 프론트매터 `status:` 한 줄만 바꾼다(`setDayColor` 의 프론트매터 편집을 일반화한 `setFrontmatterKey`).
- 모바일 하단 탭은 5개 한계가 있으므로 "오늘" → **"내 업무"**로 확장하고, "검색"은 상단 아이콘으로 옮기는 안을 제안한다(결정 필요).
- 그래프는 지금처럼 보조 기능으로 둔다.

### 4.5 건강도와 조기경보 (P2-2)

- **시스템 건강도는 파생**(기한 초과 수, 7일 이상 멈춘 일, 담당자 없는 일, 14일간 활동 없음 …). **사람이 입력한 `health:` 와 따로 표시**한다.
- **문턱은 한 곳에 둔다.** 설정을 기기 `localStorage` 가 아니라 **vault 안의 설정 노트**(예: `_workspace/설정.md` 프론트매터)에 둬서 팀원 모두 같은 값을 쓰고 동기화된다. 각 문턱에 **이유(출처)** 를 같이 적는다 — 값이 사람마다 다르면 지표가 신뢰를 잃는다.
- **같은 이름의 지표가 다른 값을 내면 위험하다.** 정의가 불확실한 지표는 만들지 않고 비워 둔다(예: 업무량).

### 4.6 결정·미결 (P2-2)

회의 노트 안의 항목을 협의 항목으로 파싱한다(질문 → 답/미결 → 닫힘).
- **상태는 문서가 갖는다.** 댓글/대화에 열림·닫힘을 두지 않는다.
- **닫을 때 결론 한 줄을 강제**한다(`=> 결론`). 결론이 비면 닫기 버튼이 잠긴다. "할 일 완료"와 "협의 결론"은 다르다는 점을 제품에 반영하는 유일한 강제다.
- `side:`(공이 누구에게 있나) + `due:`(다시 물을 날)로 "확인해 보겠다고 함"이 사라지지 않게 한다.
- 답 대기 항목은 프로젝트를 가로질러 **내 업무**에 선다.

### 4.7 타임라인 (P2-2)

노트 변경 전체가 아니라 **의미 있는 사건만** 보여 준다(생성·상태 변경·담당 변경·마일스톤·주요 결정·완료/재개·위험 등록/해결). 오탈자 수정은 올리지 않는다. 구현은 두 가지 중 선택해야 한다 → 결정 필요(아래 Q4).

### 4.8 템플릿

템플릿도 **마크다운 폴더**로 둔다(`Templates/프로젝트-행사/…`). "새 프로젝트"는 폴더를 복사하고 `{{name}}`, `{{due}}` 같은 자리표시자를 채운다. 사용자가 템플릿을 일반 노트처럼 고칠 수 있고 동기화된다. 마감일 입력 시 중간 일정을 역산하는 규칙(D-14 등)은 템플릿 프론트매터에 선언한다.

## 5. 단계별 계획

### P2-1 — 프로젝트 관리의 뼈대 (가장 먼저)
목표: "노트 + 일정 + 메모"가 "프로젝트 + 내 업무"로 **성격이 바뀌는** 최소 묶음.

1. **업무 인덱스** `work.ts`: 모든 노트의 체크리스트 → `Task`(상태·due·owner·p·proj), 타입 노트 → `Project`. 단위 테스트 포함.
2. **토큰·상태 문자 파서/직렬화**(`calendar.ts` 의 `eventLine` 패턴 재사용) + 업무 편집기(GUI). 기존 일정 파서와 충돌 없음을 테스트로 고정.
3. **프로젝트 생성/허브**: 프로젝트 노트 판정, 소속 규칙, 허브(개요·할 일·일정·문서).
4. **내 업무** 화면: 기한 초과 · 담당자 없음 · 오늘/이번 주 · 소속 없음, 각 줄에 이유 표시, 누르면 위치로 이동. 레일/모바일 탭 개편.
5. **표·칸반 뷰** + `setFrontmatterKey`.
6. **템플릿 v1**: 일반/행사/콘텐츠 3종 + 새 프로젝트 마법사.

완료 기준(숫자로): 아래 6장.

### P2-2 — 업무 문맥
협의·결정·미결(4.6) → 받은 편지함 → 타임라인(4.7) → 건강도·조기경보(4.5) → 저장된 필터/사용자 정의 뷰(GUI).

### P2-3 — 운영 관리 (보류, 프로젝트 팩)
고객·기관, 계약·청구·비용, 리소스·업무량, 보고서 템플릿, CSV/Excel 입출력, 메일·캘린더 연동. **P2-1/2 가 안정된 뒤** 특정 업무가 정해지면 팩으로 제공한다. (여기를 먼저 만들면 특정 회사 백오피스의 복제가 된다.)

### P2-4 — 조직 협업 (보류, 별도 의사결정)
서버·계정·권한·승인·감사. 파일 기반 개인 모드를 유지한 채 **선택형**으로 붙인다. 아래 7장의 한계 때문에 P2-1~2 를 "소규모 팀(공유 폴더/Git/Drive)"까지로 규정한다.

## 6. 검증 방식 (이번 프로젝트의 교훈 반영)

자동화 테스트가 없다는 점이 가장 큰 기술 부채라 Phase 2 시작과 함께 해결한다.

- **파서 단위 테스트**(vitest 도입): 토큰·상태 문자·소속 판정·기존 일정 문법과의 비충돌. 이미 경험한 사고(전체 파일이 0바이트가 된 적 있음)를 막기 위해 **파일 수정 도구는 안전한 쓰기(임시 파일→교체)**만 사용.
- **숫자 상식 검사**: 대기열 건수가 의미를 잃지 않게 **픽스처로 상한을 검사**한다(예: 기한 초과가 전체 업무의 1/4 을 넘으면 정의가 잘못된 것). 중복 제거 중 뜻이 바뀌어 건수가 폭발하는 사고가 설계 자료에도 있었다.
- **"검사가 사라지는 것"을 막는다**: 테스트가 이름 충돌 등으로 조용히 빠지지 않도록 개수 가드를 둔다.
- **실제 입력으로 시험**: 한글 입력기 문제처럼 코드 주입으로는 안 보이는 결함이 있었다. 입력이 있는 기능은 실제 키보드·한글 모드로 확인한다.
- 대량 데이터(노트 5천 개)에서 인덱스 갱신 시간 측정, 기준 초과 시 증분 갱신 도입.

## 7. 위험과 한계

| 위험 | 내용 | 대응 |
|---|---|---|
| **동시 편집·충돌** | 파일 단위 동기화라 같은 노트의 서로 다른 줄을 두 사람이 고치면 충돌 | 회의 = 사람/회의당 1파일, 받은 편지함 = 사람별 파일로 구조 유도. 충돌 UX(현재 3지선다)를 줄 단위 병합으로 개선하는 것은 P2-2 후보 |
| **작성자 신뢰성** | `owner:` 는 문자열일 뿐 인증이 아님 | 소규모 신뢰 환경 전제. 감사가 필요하면 P2-4 |
| **성능** | 모든 노트 체크리스트 인덱싱 | 파일별 해시 캐시(현재 캘린더 방식) + 측정 |
| **모바일 화면 밀도** | 탭 5개 한계, 표/칸반이 좁음 | 모바일은 목록 중심, 칸반은 가로 스크롤 열 접기 |
| **설정 위치** | 현재 설정은 기기별(`localStorage`) | 팀 공유 값(문턱·템플릿·타입)은 vault 안 노트로 |
| **복잡도 증가** | 개인 사용자가 무거워짐 | 프로젝트 기능은 "프로젝트 만들기"를 쓸 때만 보이게 점진 노출, 관리 메뉴 기본 숨김 |
| **범위 팽창** | 사내 업무 기능을 앱에 박고 싶은 유혹 | P2-3 은 "팩"으로만. 제품 코어에는 업무 고유 용어를 넣지 않는다 |

## 8. 결정 사항 (2026-11-09 확정)

| # | 결정 | 내용 |
|---|---|---|
| 1 | 1차 사용자 | **소규모 팀**(공유 폴더·Git·Drive). 조직용 서버는 P2-4 로 보류 |
| 2 | 홈(시작 화면) | **내 업무** — PC·모바일 모두 |
| 3 | 모바일 탭 | "오늘" → **내 업무**로 확장(오늘 일정 + 대기열 + 프로젝트). 검색 탭은 유지(5탭) |
| 5 | 상태 표기 | **호환성 우선**: 체크박스는 표준 `[ ]`/`[x]` 만 쓰고, 진행 중·대기·접음은 `status:` 꼬리표로. (`[~]` `[>]` 같은 비표준 문자는 쓰지 않음) |
| 6 | 담당자 | 우선 문자열(`owner:`) + 설정의 "내 이름"으로 내 것을 가림. 사람 노트(`type: person`) 링크는 뒤로 미룸 |

미결(나머지): 4 타임라인 구현 방식, 7 P2-1 범위 쪼개기(→ 업무 인덱스·내 업무를 먼저 낸 상태), 8 이전 Codex 스레드 가져오기.

### (원래 질문 목록) 결정이 필요했던 것

1. **1차 사용자**: 개인 / 소규모 팀(2~10명, 공유 폴더·Git·Drive) / 조직. (이 계획은 소규모 팀까지를 P2-1~2 로 가정)
2. **홈(시작 화면)**: PC·모바일 모두 "내 업무"로 바꿀까, 캘린더/오늘을 유지할까.
3. **모바일 탭**: "오늘"을 "내 업무"로 확장하고 "검색"을 상단 아이콘으로 옮겨도 되는가.
4. **타임라인 구현**: ① 노트의 프론트매터·`status` 변경을 **파싱 가능한 활동 로그 노트**(`_activity/…md`)에 자동 추가(읽을 수 있고 동기화되지만 노이즈 관리 필요) ② 동기화(GitHub 커밋 이력 등)에서 파생(서버 없이 가능하나 제공자마다 다름) 중 어느 쪽.
5. **상태 문자 호환**: `[~]` `[>]` `[-]` 를 쓰면 일반 마크다운 뷰어에서는 체크박스로 안 보인다(Obsidian Tasks 호환). 허용 가능한가, 아니면 `[ ]` + 토큰(`status:doing`)만 쓸까.
6. **담당자 모델**: 문자열 / vault 안 사람 노트(`type: person`)로 링크. 후자가 이름 변경·집계에 유리하지만 입력이 번거롭다.
7. **P2-1 범위**: 6개 작업을 모두 한 번에 낼지, 업무 인덱스+내 업무(1~4)를 먼저 낼지.
8. **이전 Codex 스레드**(백오피스 기획 5단계 산출물, 방법론 v0.9)를 근거로 더 가져올 것인가.

## 9. 바로 시작하면 하는 일 (P2-1 첫 스프린트 제안)

1. vitest 도입 + `work.ts` 파서와 테스트(기존 `calendar.ts` 와 비충돌).
2. `Task`/`Project` 타입, 소속 규칙, 업무 인덱스 + 간단한 "내 업무" 목록(읽기 전용).
3. 업무 한 줄 편집기와 `setFrontmatterKey`.
4. 프로젝트 허브(읽기) → 칸반(상태 이동).
5. 템플릿 v1과 새 프로젝트 마법사.

각 단계마다 PC·Android 실기에서 확인하고, 문서(README·docs)를 같이 갱신한다.
