# Codex 제안 (원문)

두 자료를 함께 보면 방향이 꽤 선명합니다.

MD Reader를 “노트 앱에 프로젝트 기능을 추가한 제품”으로 만들기보다는, **마크다운을 업무 원장으로 사용하는 로컬 우선 프로젝트 운영 앱**으로 발전시키는 편이 좋습니다.

현재 강점인 노트·일정·링크·검색·파일 소유권은 유지하면서, 백오피스의 복잡한 업무를 그대로 복제하지 말고 범용 구조로 추상화하는 방식입니다.

## 추천 제품 정의

> 문서, 일정, 할 일, 결정, 파일, 업무 상태가 하나의 프로젝트 안에서 연결되는 로컬 우선 프로젝트 운영 앱

Notion처럼 자유롭지만 더 파일 중심이고, Jira처럼 관리할 수 있지만 티켓 작성을 강요하지 않는 포지션입니다.

## 가장 중요한 변화: 노트를 ‘업무 객체’로 승격

현재는 모든 것이 `NoteFile`입니다. 여기에 별도 DB를 만들기보다 프론트매터를 이용해 노트에 타입을 부여하는 방식을 추천합니다.

```md
---
type: project
status: active
owner: 홍길동
start: 2026-11-01
due: 2027-02-28
client: 한국문화재단
health: warning
tags: [공모전, 운영]
---

# 2027 문화콘텐츠 공모전
```

예를 들어 다음 타입을 기본 제공할 수 있습니다.

- `project`: 프로젝트
- `task`: 할 일
- `meeting`: 회의·통화 기록
- `decision`: 결정사항
- `issue`: 문제·위험
- `client`: 고객·기관
- `contract`: 계약
- `invoice`: 청구·입금
- `report`: 보고서
- `resource`: 사람·거래처·장비

중요한 점은 실제 저장 결과가 계속 사람이 읽을 수 있는 `.md`라는 것입니다.

이 구조를 만들면 같은 파일을 다음처럼 여러 방식으로 볼 수 있습니다.

- 문서로 보기
- 표로 보기
- 칸반으로 보기
- 캘린더로 보기
- 타임라인으로 보기
- 대시보드에서 집계하기

즉, 새 기능을 계속 따로 만드는 대신 **하나의 데이터에 여러 뷰를 제공하는 앱**이 됩니다.

## 백오피스 자료에서 가져올 핵심 아이디어

### 1. ‘오늘’이 아니라 ‘내 업무’ 화면

백오피스 자료에서 가장 강한 발견은 “사업을 하나씩 열어 밀린 일을 찾으면 결국 놓친다”는 점입니다.

현재 `오늘` 화면을 다음과 같은 통합 업무함으로 확장할 수 있습니다.

- 오늘 할 일
- 기한이 지난 일
- 답변을 기다리는 항목
- 내가 답해야 하는 항목
- 결정되지 않은 회의 안건
- 종료됐지만 보고되지 않은 프로젝트
- 일정은 잡혔지만 담당자가 없는 일
- 최근 변경된 중요 문서
- 동기화 충돌 및 데이터 이상

이 목록은 별도 알림 데이터로 저장하지 않고, 현재 원칙대로 원본 노트에서 매번 파생하면 좋습니다.

핵심 UX는 세 가지입니다.

- 왜 이 항목이 여기에 나타났는지 표시
- 누르면 처리할 정확한 위치로 이동
- 완료하면 목록에서 자동으로 사라짐

### 2. 프로젝트 허브

프로젝트 하나를 열면 단일 문서가 아니라 다음 내용을 모아 보여주는 허브가 됩니다.

- 개요
- 해야 할 일
- 일정
- 문서
- 회의·결정
- 파일과 링크
- 위험·이슈
- 활동 기록
- 비용·계약
- 프로젝트 멤버

모든 프로젝트에 탭을 강제할 필요는 없습니다. 프로젝트 템플릿에 따라 필요한 탭만 보여주면 됩니다.

예:

- 일반 프로젝트: 개요·할 일·일정·문서·회의
- 영업 프로젝트: 고객·접촉·제안·결과
- 행사 프로젝트: 준비·접수·심사·시상·보고
- 콘텐츠 프로젝트: 기획·제작·검수·게시
- 내부 프로젝트: 목표·업무·결정·회고

백오피스 자료의 특정 업무명을 제품에 박아 넣지 않고, 프로젝트 유형별 템플릿으로 일반화하는 방식입니다.

### 3. 회의록보다 ‘결정과 미결’ 관리

백오피스의 협의 기록 설계는 범용 앱에도 매우 잘 맞습니다.

회의 노트 안에 다음 구조를 둘 수 있습니다.

```md
## 안건

- [decision] 보도자료는 내부에서 초안 작성
- [waiting] 상장 재고 확인
  owner-side: client
  due: 2026-11-12
- [issue] 영상 이벤트 중복 수상 정책 미정
```

앱은 이를 파싱해서 자동으로 구분합니다.

- 결정된 것
- 답을 기다리는 것
- 다시 확인할 날짜가 지난 것
- 프로젝트 범위를 변경하는 것
- 비용이나 일정에 영향을 주는 것

특히 항목을 닫을 때 `결론`을 요구하는 기능은 매우 좋습니다.

> 할 일을 완료하는 것과, 협의를 결론 내는 것은 다르다.

이 차이를 제품에 반영하면 일반 노트 앱과 확실히 달라집니다.

### 4. 프로젝트 건강도와 조기경보

단순 진행률보다 “먼저 움직이는 숫자”를 보여주는 대시보드가 좋습니다.

범용 지표 예시:

- 기한 초과 업무 수
- 담당자 없는 업무 수
- 7일 이상 멈춘 업무
- 답변 대기 초과
- 이번 주 예정 작업량 대비 완료량
- 일정이 임박했지만 선행 작업이 안 된 항목
- 최근 14일간 활동 없는 활성 프로젝트
- 예산 소진율 대비 진행률
- 동기화되지 않은 변경
- 충돌 또는 잘못된 참조

건강도는 사용자가 직접 입력하기보다 우선 파생값으로 계산합니다.

```text
정상: 기한 초과 없음
주의: 기한 초과 1~2건 또는 7일간 활동 없음
위험: 핵심 마일스톤 초과 또는 차단 이슈 존재
```

단, 자동 판정과 사람이 판단한 상태는 구분해야 합니다.

- 시스템 건강도: 계산된 상태
- 담당자 판단: 사람이 입력한 상태

### 5. 두 개의 탐색 축

백오피스 설계의 “사업 축과 소관 축”도 범용적으로 적용할 가치가 있습니다.

같은 일을 두 방향에서 찾게 합니다.

- 프로젝트별: 이 프로젝트에는 무슨 일이 있는가?
- 업무영역별: 전체 프로젝트에서 내가 담당하는 일은 무엇인가?

예를 들면:

```text
프로젝트
  A 프로젝트
  B 프로젝트

업무
  내 업무
  일정
  회의·결정
  위험
  보고
  고객
```

사용자가 프로젝트를 30개 관리해도 매번 프로젝트를 열어보지 않도록 해야 합니다.

홈

  캘린더

프로젝트

## 강력한 차별화 기능 아이디어

### 프로젝트 템플릿

템플릿이 폴더, 문서, 상태, 기본 일정을 함께 생성합니다.

예:

```text
행사 운영 프로젝트 생성
├─ 프로젝트 개요.md
├─ 일정.md
├─ 회의/
├─ 계약/
├─ 보고/
├─ 접수/
└─ 프로젝트 회고.md
```

마감일을 입력하면 중간 일정을 역산하는 기능도 유용합니다.

```text
행사일 D
심사 완료 D-14
접수 마감 D-30
홍보 시작 D-60
제작 발주 D-75
```

### 받은 편지함

정리하기 전 모든 것을 빠르게 넣는 곳입니다.

- 메모
- 파일
- URL
- 스크린숏
- 음성 메모
- 이메일에서 복사한 내용
- 아직 프로젝트가 정해지지 않은 할 일

이후 프로젝트·담당자·날짜를 붙여 정리합니다. 실제 업무에서는 “입력하는 순간 분류해야 하는 부담”이 사용을 막기 때문입니다.

### 연결된 업무 문맥

할 일을 열면 제목만 보여주지 않고 다음을 함께 보여줍니다.

- 소속 프로젝트
- 관련 문서
- 결정 근거
- 최근 회의
- 선행·후행 작업
- 관련 파일
- 담당자
- 변경 이유

예를 들어 “견적 수정”이라는 할 일 옆에 “11월 8일 회의에서 범위 추가 결정”이 붙는 구조입니다.

### 변경 이력과 타임라인

Git처럼 모든 변경을 보여주면 노이즈가 너무 큽니다. 백오피스 자료의 원칙처럼:

> 저장은 전부 하되, 표시할 사건은 골라낸다.

타임라인에는 다음 정도만 표시하는 것이 좋습니다.

- 프로젝트 생성
- 상태 변경
- 담당자 변경
- 마일스톤 변경
- 주요 결정
- 업무 완료·재개
- 파일 연결
- 위험 등록·해결

오탈자 수정 같은 편집은 타임라인에 올리지 않습니다.

### 사용자 정의 속성과 뷰

궁극적으로는 사용자가 다음을 만들 수 있어야 합니다.

```yaml
type: project
fields:
  status: select
  owner: person
  due: date
  client: relation
  budget: currency
  health: computed
```

그리고 저장된 필터를 만들 수 있습니다.

- 내가 담당한 진행 중 프로젝트
- 이번 달 종료 예정
- 고객 답변 대기
- 예산 80% 이상 소진
- 보고서 미완료
- 14일간 활동 없음

이는 Dataview처럼 강력하되, 사용자가 쿼리를 쓰지 않아도 GUI로 만들 수 있어야 합니다.

## 현재 구조에서 반드시 결정해야 할 문제

현재 앱의 “서버 없음·사용자 계정 없음·파일 단위 동기화” 원칙은 개인용에는 매우 좋지만, 본격적인 백오피스 협업에는 한계가 있습니다.

특히 다음 기능은 현재 구조만으로 안정적으로 제공하기 어렵습니다.

- 동시 편집
- 사용자별 권한
- 작성자·담당자 신뢰성
- 승인 워크플로
- 감사 로그
- 여러 사람의 실시간 알림
- 일부 프로젝트만 공유
- 관리자 통제

따라서 제품을 두 단계로 나누는 것을 권합니다.

### 1단계: 개인·소규모 팀용 로컬 우선

- 파일 기반 유지
- 공유 폴더 또는 Git/Drive 동기화
- 담당자는 문자열 또는 로컬 연락처
- 충돌은 파일 단위
- 승인 대신 상태와 체크리스트
- 운영비 없음

### 2단계: 조직용 선택형 워크스페이스 서버

- 로그인·조직·팀
- 역할과 권한
- 이벤트 단위 변경 이력
- 실시간 알림
- 승인·검토
- API 및 외부 시스템 연동
- 서버와 로컬 파일 간 동기화

중요한 것은 2단계를 위해 처음부터 앱 전체를 서버형으로 바꾸지 않는 것입니다. 파일 기반 개인 모드가 제품의 차별점이므로 유지하고, 조직 기능을 선택형으로 붙이는 편이 좋습니다.

## 추천 개발 우선순위

### 1차: 프로젝트 관리의 뼈대

- 노트 타입과 프론트매터 스키마
- 프로젝트 생성 및 프로젝트 허브
- 할 일에 담당자·마감일·우선순위·상태 추가
- `내 업무` 통합 화면
- 표·목록·칸반 뷰
- 프로젝트 템플릿

### 2차: 업무 문맥

- 회의·결정·미결 항목
- 프로젝트 활동 타임라인
- 노트·일정·할 일·파일 관계 연결
- 받은 편지함
- 저장된 필터와 사용자 정의 뷰
- 프로젝트 건강도

### 3차: 운영 관리

- 고객·기관
- 계약·청구·비용

- 보고서 템플릿
- CSV·Excel 가져오기/내보내기
- Google Drive·메일·캘린더 연결

### 4차: 조직 협업

- 선택형 서버
- 사용자·팀·권한
- 승인 흐름
- 감사 기록
- 실시간 공동 작업
- 웹훅·API

## 가장 추천하는 첫 번째 구현

지금 하나만 고른다면 **“프로젝트 타입 + 내 업무 화면 + 프로젝트 허브”**입니다.

이 세 가지가 생기면 앱의 성격이 바로 바뀝니다.

```text
현재
노트 + 일정 + 메모

변경 후
프로젝트
 ├─ 문서
 ├─ 할 일
 ├─ 일정
 ├─ 회의·결정
 ├─ 파일
 └─ 활동 기록
        ↓
    내 업무에서 통합
```

반대로 계약·정산·고객관리부터 만들면 특정 회사의 백오피스를 복제한 무거운 제품이 될 가능성이 큽니다. 먼저 범용 업무 객체와 뷰를 만들고, 계약·정산·입찰 같은 기능은 그 위에 얹는 “프로젝트 팩”으로 제공하는 편이 확장성이 좋습니다.

제품을 한 문장으로 표현하면 이렇습니다.

> **MD Reader는 노트를 보관하는 앱이 아니라, 문서에서 실제 업무가 움직이게 만드는 프로젝트 운영 앱이 된다.**
